**读法**

- 档位之间 GPU 时间单调递增，Low → Ultra 约 2.7–4.2 倍（湖区最小）；Draw Call 的差距主要来自点光源阴影（每盏 6 个立方体面），入口 Ultra 是 Low 的 2.3 倍。
- 修复 CASE-05 后，High 的 GPU 时间上升约 11–16%（入口 1.80 → 2.06 ms）：原来图集装不下，URP 把每张阴影偷偷降了分辨率；现在 High 真的在画 512² 的阴影。**变慢是“正确”的代价**，这次变化需要在回归记录里注明原因，而不是当作回退。
- M5 Max 上所有档位都远超 60 fps，这台机器只适合看**相对变化**；档位上限和预算要在 GTX 1070 Ti 上定。

环境：Mines and Cave Set + Starter Assets 机器人角色，1261 件拼装件；白模方块保留为不可见的碰撞体，路径、机位、PerfZone 与白模完全一致，所以前后可以直接对比。完整表：[mac/tiers_art.md](mac/tiers_art.md)。

| --- | --- | --- | --- | --- |
| Low | 1.13 / 1.14 / 1.16 | 0.68 / 0.69 / 0.81 | 525 / 443 / 266 | 533 / 320 / 123 |
| Medium | 1.11 / 1.21 / 1.44 | 1.11 / 0.97 / 1.27 | 577 / 485 / 298 | 612 / 356 / 144 |

| Ultra | 3.03 / 2.01 / 3.17 | 2.87 / 1.88 / 2.97 | 1123 / 941 / 624 | 1199 / 735 / 388 |

**读法**

- 熔炉和湖区 Draw Call 增加最多（熔炉 Low 123 → 266）：白模是几个大方块，现在是成百上千个拼装件。入口反而略降，因为地面和天花板关掉了阴影投射，点光源的 6 个阴影面少画了一大批物体。
- High 的 GPU 时间反而比白模低 10–18%（入口 2.06 → 1.71 ms），原因同上：阴影阶段是 High 的主要开销，关掉地面 / 天花板投影省下的比新增模型多。
- Low 档绝对值上升约 0.4 ms，主要是贴图采样和顶点数增加；M5 Max 上仍是 800+ fps 量级，真正的预算要到 GTX 1070 Ti 上定。
- 四档阴影图集都没有溢出警告（CASE-05 的检查）。
- **1% Low 这次不作为结论**：采集时机器上开着浏览器、其他客户端（负载 4.5–9.5），High / Ultra 出现约 450 个仅 CPU 侧的 >5 ms 帧，GPU 侧为 0，典型的外部干扰，见 [CASE-09](../cases/CASE-09-concurrent-build-contamination.md)。GPU 平均值不受影响，可以对比。

PSO 预热（High，冷缓存，各 3 次）：无 GSC 入口首段峰值 81 / 87 / 82 ms，有 GSC 7 / 18 / 5 ms；GSC 预热 187 个状态，耗时 1.1 s（第一次 2.6 s，当时机器负载较高）。结论与白模一致。

## PSO 预热实验

问题：GraphicsStateCollection（GSC）预热到底能不能消除“第一次看到某个效果”的卡顿？

方法：High 档，`-perf-warmup 0`（跑图一开始就记录），**每次运行前清空 Metal 着色器缓存**，有 / 无 GSC 各跑 3 次。

| | 无 GSC（3 次） | 有 GSC（3 次） |
| --- | --- | --- |
| > 16.7 ms 的帧 | 4 / 3 / 4 个 | 1 / 0 / 0 个 |
| 入口区域首段峰值 | 71.5 / 71.5 / 71.2 ms | 3.7 / 4.0 / 3.5 ms |
| 入口 1% Low | 231 / 238 / 235 fps | 376 / 368 / 373 fps |
| 熔炉首次出现岩浆 / 火焰 | 19–26 ms | 无卡顿 |
| 启动时额外耗时 | 0 | WarmUp 914–922 ms（128 个状态） |

结论：

1. GSC 消除了入口两帧 ~71 / ~48 ms 和熔炉 ~20 ms 的 PSO 编译卡顿，入口 1% Low 提升约 60%。
2. 代价是启动多 0.9 秒，应放在加载画面里。
3. 地下湖偶发一个 12–26 ms 的帧（约每两次运行一次，有无 GSC 都有）。已排除 PSO、GPU、场景位置和 GC，只在 CPU 侧，见 [CASE-08](../cases/CASE-08-lake-hitch-and-runner-garbage.md)。
4. 实验第一次得到的结论是“GSC 让峰值更糟（1150 vs 1020 ms）”——那是测量工具的错误，见 [CASE-07](../cases/CASE-07-frame-timing-double-count.md)。

## 噪声与回归阈值

同一个包、同一档位（High）连续跑两次，`compare.py` 的区域 GPU 平均差：入口 +0.4%、湖 +4.9%、熔炉 +1.8%。

- 帧时间只有 1.5–2 ms 时，系统调度、温度、后台进程造成的抖动就有好几个百分点，**默认 5% 阈值在 M5 Max 上会误报**。
- 建议：
  - Mac（帧时间 < 3 ms）：阈值 8%，并且要求连续两次运行都超阈值才报警；
  - GTX 1070 Ti（预计帧时间 5–15 ms）：先用 5%，拿到 3 次重复运行的噪声后再定；
  - 阈值按“平台 × 档位”记录在本页，修改时写明依据。
- 已落地：阈值写在 `Packages/com.zfw.perfrunner/Tools~/thresholds.json`，按设备 / API / 档位匹配，每条规则必须写明依据；`compare.py` 不带 `--threshold` 时自动选用并打印来源。目前规则：Apple → 8%，其余 → 5%。
- 实测：修复后两次相同的 High 运行（Mac）差异 +1.7% / +2.3% / +3.6%，在 8% 内通过。
- 回归记录见 [regressions.md](regressions.md)。

## CSV 格式

`frame,zone,cpu_ms,gpu_ms,draw_calls,setpass_calls,gfx_mem_mb,gc`

- `cpu_ms` / `gpu_ms` 为空：这一帧没有新的已完成帧时间（CASE-07），分析工具按缺失值处理。
- `gc`：这一帧发生的 GC 次数（CASE-08）。PerfRunner 本身每帧零分配，所有格式化在采集结束后进行。
