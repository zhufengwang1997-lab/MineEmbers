# 第一部分：关键代码

## 1. 原生插件的生命周期

`GpuCaps.cpp:41-112`

**在干什么**
- `UnityPluginLoad`（`:88-95`）：保存 `IUnityInterfaces*`，取 `IUnityGraphics`，注册设备事件回调，**再手动调用一次 Initialize**。
- `OnDeviceEvent`（`:74-82`）：Initialize → `Collect()`；Shutdown → 清空缓存。
- `Collect`（`:41-72`）：`GetRenderer()` 分派到对应后端；不支持的 API 写 `error` 让 C# 兜底。
- 两个导出函数在锁内读缓存（`:104-112`）。

**为什么这样写**
- **不在 `UnityPluginLoad` 里直接碰设备**（文件头注释 `:5`）：插件如果被设为"启动时加载"，这时设备可能还没建。按规范应该等 Initialize 事件。
- **但又手动补一次 Initialize**（`:92-94`）：本项目的插件是在 C# 第一次 `[DllImport]` 时才加载的，那时设备早就建好，事件已经错过了。两种加载时机都要兼容。
- **采集一次、缓存 JSON**：能力不会在运行中变化（设备重建除外），每次调用重新查没必要；而且查询要在有设备的时机做。
- **互斥锁**：设备事件在渲染线程上来，C# 在主线程读，两个线程可能同时访问字符串。

**换种写法会怎样**
- 每次 C# 调用时现查：要求 C# 调用发生在渲染线程或能安全拿到设备的时候——在 Unity 里很难保证。
- 返回结构体而不是 JSON：省一次序列化，但 C# 和 C++ 两边的内存布局必须严格一致，加字段就要两边同时改；JSON 加字段旧代码会直接忽略，更适合"跨版本、跨语言、还要落盘做矩阵"的场景。

**可能踩的坑**
- 返回的 `const char*` 指向 `std::string` 内部缓冲，**下次设备事件就可能失效**（`:103` 注释）→ C# 必须立即复制。
- `UnityPluginUnload` 里一定要注销回调，否则编辑器里重载域之后回调指向已卸载的代码 → 崩溃。

## 2. Metal 后端：统一内存下的"显存"和特性分层

`CapsMetal.mm:26-67`；`UnityMetalBridge.mm:9-15`

**在干什么**：从 `MTLDevice` 读名字、显存预算、OS 版本（当驱动版本）、GPU Family，按规则把每个特性归为 supported / unsupported / emulated。

**关键判断**
| 特性 | 判据 | 为什么 |
| --- | --- | --- |
| 显存 | `recommendedMaxWorkingSetSize` | Apple Silicon 是统一内存，没有"独立显存"；这是 Metal 建议的 GPU 常驻资源预算，最接近显存的概念（`:37-39`） |
| 驱动版本 | macOS 版本号 | Metal 驱动随系统发布（`:44`） |
| 光追 | `supportsRaytracing` + Apple9 | API 从 M1（Apple7）就有，但**硬件光追单元**从 M3（Apple9）才有；之前是计算着色器模拟 → emulated（`:54-57`） |
| VRS | `supportsRasterizationRateMap` | Metal 的可变速率是"屏幕空间光栅化率图"，和 D3D12 的逐图块/逐绘制 VRS 不完全对应 |
| Mesh Shader | Metal 3 family | Metal 3 引入 object/mesh 管线 |
| Bindless | Argument Buffers Tier 2 | 大型、GPU 可写的资源表 |

**为什么需要 `UnityMetalBridge.mm`**：Unity 的 Metal 接口头文件里有 `id<MTLDevice>` 这种 Objective-C 类型，只能在 `.mm` 里包含。把它隔离在一个文件里，`GpuCaps.cpp` 保持纯 C++，Windows 上也能编。还按 `V2 → V1 → 无版本号`的顺序取接口（旧接口已弃用），兼容不同版本的 Unity 播放器。

**换种写法会怎样**：用 `SystemInfo.graphicsMemorySize` → 在 Mac 上得到的是 Unity 的估计值，含义不明确；用 `MTLDevice.currentAllocatedSize` → 是"已经用了多少"，不是"能用多少"。

**可能踩的坑**
- 厂商 ID：Apple GPU 不报 PCI 厂商号，代码用名字推断（`:36`），老的 Intel Mac 上的 AMD/Intel GPU 靠名字里的字符串识别——不严谨，但目标平台是 Apple Silicon。
- 同一块 M5 Max，MoltenVK 报的是 DEVICE_LOCAL 堆大小（49152 MB），Metal 报的是工作集预算（38338 MB）——**所以显存阈值必须注明取自哪个 API**（CASE-01）。

## 3. Vulkan / D3D12 后端

`CapsVulkan.cpp:46-100`；`CapsD3D12.cpp:46-95`

**Vulkan 在干什么**
- **不链接 Vulkan Loader**：用 Unity 给的 `getInstanceProcAddr` 自己加载 4 个函数（`:50-55`）。CMake 里只要 Vulkan **头文件**（`CMakeLists.txt:32` 注释 "headers only; entry points come from Unity"）。
- 显存 = 所有 `DEVICE_LOCAL` 堆之和（`:68-74`）；集显上这个堆其实就是系统内存。
- Bindless = 四个 descriptor indexing 特性同时为真（`:85-94`），通过 `VkPhysicalDeviceFeatures2.pNext` 链查询。
- 光追 / VRS / Mesh Shader = 对应扩展是否存在（`:96-100`）。
- 驱动版本按厂商解码（NVIDIA 的版本号位域和标准 `VK_VERSION` 不同）。

**D3D12 在干什么**
- 从设备的 LUID 反查 DXGI 适配器（`:51-55`）→ 名字、厂商、`DedicatedVideoMemory`。
- OS 版本用 `RtlGetVersion`，因为 `GetVersionEx` 在没有清单文件时会"撒谎"（`:66`）。
- `CheckFeatureSupport`：`OPTIONS` 的资源绑定档次 Tier 3 = 完全 Bindless（`:77-81`）；`OPTIONS5` 光追档次；`OPTIONS6` VRS 档次……
- **Pascal（GTX 10 系）上 DXR 由驱动用计算着色器实现**，报告为 emulated（`:85-91`）——这是给 GTX 1070 Ti 准备的判断。

**为什么这样写**
- 用 Unity 的函数指针：保证我们查询的是 **Unity 正在用的那个** Vulkan 实例和物理设备；自己加载 Loader 可能拿到不同的实现，还会多一份依赖。
- 记录原生档次（`raw` 字段）：中台写兼容规则时，常常需要比"supported"更细的信息（比如 ResourceBindingTier 2 和 3 的区别）。

**可能踩的坑**
- ⚠️ **Windows DLL 尚未编译，D3D12 / Vulkan 两个后端都没有在真机上跑过**，以上逻辑只经过代码审阅。面试时要如实说"写好了，Windows 实测是下一步"。
- "扩展存在"≠"特性可用"：严格做法还要查对应的 features 结构体（比如 `rayTracingPipeline` 布尔值），这里对光追/VRS 只查了扩展名——可以作为改进点。

## 4. 报告结构与手写 JSON

`CapsReport.h:13-79`

**在干什么**：定义与 API 无关的 `Report`（api、gpu、driver、os、有序的 features、error），一个 `Set` 方法插入或覆盖特性，`ToJson` 手写序列化，`JsonEscape` 处理特殊字符。

**为什么这样写**
- **`schema` 版本号**：报告会被保存下来、跨版本合并成矩阵；以后改结构时，工具能识别旧格式（`caps_merge.py` 的 `SUPPORTED_SCHEMA = {1}`）。
- **features 用有序的 `vector<pair>`** 而不是 `map`：输出顺序稳定，两份报告做文本对比时不会因为顺序不同出现假差异。
- **手写 JSON**：只有几十行，不引入第三方库（插件越小越好，也避免和 Unity 或其他插件的同名库冲突）。
- **`error` 字段**：查询失败一半时，不是整个失败，而是带着已知信息和错误原因返回。

**换种写法会怎样**：用 nlohmann/json → 代码更短，但多一个依赖；用二进制格式 → 体积小，但人读不了，失去"报告本身就是文档"的价值。

**可能踩的坑**：GPU 名字里可能有引号或控制字符 → 必须转义（`:41-57`），否则 C# 解析失败、整个报告丢失。

## 5. 插件构建：符号可见性与 macOS Bundle

`CMakeLists.txt:11-35`

**要点**
- `CMAKE_CXX_VISIBILITY_PRESET hidden`（`:13-14`）：默认隐藏所有符号，只有标了 `UNITY_INTERFACE_EXPORT` 的函数对外可见。避免和 Unity 或其他插件里的同名函数冲突，也让二进制更小。
- macOS 上必须是 `MODULE` + `BUNDLE`（`:21-28`），产出 `GpuCaps.bundle`，Unity 才认。同时编 `arm64;x86_64` 两种架构（Universal）。
- `.mm` 文件开 ARC（`-fobjc-arc`，`:29`），所以 `CapsMetal.mm` 用 `__bridge` 做 `void*` 和 `id` 之间的转换，不转移所有权。
- Windows 上链接 `dxgi`、`d3d12`，Vulkan 只要头文件（`:32-35`）。
- Unity 插件头文件的位置要用 `-DUNITY_PLUGIN_API=` 传入，找不到就直接报错（`:6-9`）。

**坑**：C# 里 `[DllImport("GpuCaps")]` 不写扩展名，Unity 会在 macOS 上找 `.bundle`、Windows 上找 `.dll`（`GpuCaps.cs:16-17` 注释）。插件文件的 `.meta` 里还要勾选正确的平台，否则打包时不会被带上。

## 6. C# 侧 P/Invoke 与兜底

`GpuCaps.cs:19-74`

**在干什么**
```csharp
IntPtr p = GpuCaps_GetReportJson();
string json = p == IntPtr.Zero ? null : Marshal.PtrToStringUTF8(p);   // 立即复制
r = JsonUtility.FromJson<GpuCapsReport>(json);
...
catch (Exception e) when (e is DllNotFoundException || e is EntryPointNotFoundException)
...
if (r == null || string.IsNullOrEmpty(r.api)) r = FromSystemInfo(r?.error);
FillUnity(r);
```

**为什么这样写**
- 返回 `IntPtr` 再手动转字符串，而不是直接声明返回 `string`：直接返回 `string` 时，.NET 的封送层会尝试**释放**这块原生内存（用 `CoTaskMemFree`），而这块内存属于 C++ 的 `std::string` → 崩溃。
- 只捕获"找不到 DLL / 找不到入口"两种异常：插件没打进包、平台不支持时优雅降级；其他异常（真正的 bug）照样抛出。
- 兜底报告里原生才能拿到的字段写 "unknown (no native plugin)" 而不是 "unsupported"——**"不知道"和"不支持"是两回事**，选档逻辑不能把"不知道"当成"不支持"。
- `source` 字段标出报告来源，方便统计时区分。

**换种写法会怎样**：插件不可用时直接报错停止 → 编辑器里用 D3D11 或 OpenGL 时整个游戏跑不起来，开发体验很差。

**可能踩的坑**：`JsonUtility` 不支持字典，所以 features 在 JSON 里是对象、在 C# 里是固定字段的类（`FeatureSet` 有 bindless、raytracing 等成员，`GpuCapsReport.cs:42-44`）——加新特性时 C# 类也要加字段，否则会被静默丢弃。

## 7. 选档：硬件上限 × 测速 × 兼容上限

`TierSelector.cs:12-53`；`TierBenchmark.cs:21-65`；`GameBootstrap.cs:21-52`；`QualityTiers.cs:44-54, 137`

**在干什么**：最终档位 = `min(测速档, 硬件上限, 兼容上限)`。

```csharp
// TierBenchmark.cs:25-26, 55-56
bool discrete = TierSelector.IsDiscreteLike(caps.gpu.vendorId, caps.gpu.name);
Tier cap = TierSelector.CapFromHardware(caps.gpu.dedicatedMemoryMB, discrete);
...
Tier bench = TierSelector.FromBenchmark((float)ms);
Tier final = TierSelector.Min(bench, cap);
// QualityTiers.Set 里再 ApplyCompatCap → 和兼容规则的上限取 min
```

**为什么这样写**
- **纯逻辑和 Unity 调用分开**：`TierSelector` 里没有任何 Unity API（`:7` 注释），可以在 EditMode 里直接单元测试各种边界。
- **三重保险**：测速反映真实性能，但测不出"显存不够时后期才会爆"的问题 → 硬件上限兜底；测速和硬件都正常，但某驱动有已知 bug → 兼容上限兜底。
- **测速在最重的区域（熔炉）、以 High 跑**：用最坏情况定档，玩家在其他区域只会更流畅。
- **用 GPU 时间而不是帧率**：帧率受 CPU、VSync、后台程序影响；GPU 时间更接近"显卡能力"。
- **保存结果，GPU 或驱动变了才重测**：避免每次启动都等 5 秒；换卡或升级驱动后性能可能变化，所以要作废。
- **把决策和输入全部写进日志**（`:57-58`）：玩家反馈"自动选档选错了"时能直接从日志看出是哪个环节导致的。

**换种写法会怎样**
- 只查数据库（按 GPU 型号映射档位）：不用测速，但新显卡、笔记本降频版本、过热都处理不了；业界常常是"数据库 + 测速"结合。
- 运行中动态调档（发现掉帧就降）：体验更好，但要防止在两档之间来回抖动（加迟滞和冷却时间）。本项目没做。

**可能踩的坑**
- ⚠️ 阈值 11/14/20 ms **没有在目标机上标定过**（M5 Max 上 High 只有约 2 ms，全部选 Ultra）。
- 测速期间的前 1 秒丢弃（`t > warmup`），但没有像 PerfRunner 那样按时间戳去重——同一帧可能被算两次，对平均值影响不大，但不严谨。

## 8. 档位扩展点 `SerializeReference`

`TierSettings.cs:30-59`；`Assets/Scripts/Rendering/MineTierExtension.cs`

**在干什么**
```csharp
[SerializeReference] public List<TierExtension> extensions;
public T Get<T>() where T : TierExtension { ... }

// 游戏侧
[Serializable] public class MineTierExtension : TierExtension { public bool heatHaze = true; public bool lakeReflection = true; }
```

**为什么这样写**
- **包里不能出现"热浪""湖面反射"这种游戏特有的字段**，否则第二个游戏（《荒原伙伴》）用这个包时会背上一堆无关字段。
- 普通的 `[SerializeField] List<Base>` 只能存基类的字段（子类字段会丢）；`[SerializeReference]` 按**引用**序列化，记录每个元素的实际类型，多态才能保存下来。

**换种写法会怎样**
- 包里留一个 `Dictionary<string, float>` 存自定义参数：灵活但没有类型检查，拼错名字不会报错。
- 每个游戏继承 `TierSettings`：一个资源只能有一个类型，两个独立模块各想加字段时会冲突；扩展列表可以同时挂多个。

**可能踩的坑**：`SerializeReference` 存的是**类的全名**，重命名或换命名空间后资源里的数据会丢失 → 需要 `[MovedFrom]` 特性做迁移。

## 9. 兼容规则的匹配与合并

`CompatOverrides.cs:42-66`；`QualityTiers.cs:114-137`

**在干什么**
- 每条规则：api、厂商、驱动区间（都可为空 = 不限）→ 命中的规则里，`disable` 取并集，`maxTier` 取最小，`case` 编号全部记下。
- 版本比较逐段按数字比（`"566.36" < "572.16"`，缺的段当 0）。
- 文件允许直接写数组，代码会自动包一层 `{"rules": ...}`（`:32-33`），因为 `JsonUtility` 要求根是对象。

**为什么这样写**
- **数据驱动**：发现某驱动有问题时，改 JSON 就能发热更新，不用改代码重新发版。
- **每条规则必须引用案例编号**：一年后有人问"这条为什么存在""现在能不能删"时，有据可查。
- 多条规则命中时采用"最保守"合并（并集、取最小），不会因为规则顺序产生歧义。

**换种写法会怎样**：用字符串比较版本 → `"9.0" > "10.0"`，经典的错。

**可能踩的坑**
- ⚠️ **当前规则文件不存在，规则数为 0**。简历上"兼容回退方案"如果指的是"回退机制"，可以讲；如果指的是"已上线的回退规则"，没有证据。
- 厂商用名字匹配（`VendorName`），新厂商（比如 Qualcomm `0x5143`）会落到 "Other"。

## 10. PerfRunner 的采集循环

`PerfRunner.cs:57-165`

**在干什么**（核心片段 `:108-135`）
```csharp
int gcNow = GC.CollectionCount(0); int gcThisFrame = gcNow - gcCount; gcCount = gcNow;
z.Evaluate(t / secondsPerZone, out var p, out var q); cam.transform.SetPositionAndRotation(p, q);
FrameTimingManager.CaptureFrameTimings();
float cpu = NaN, gpu = NaN;
if (GetLatestTimings(1, _ft) > 0 && _ft[0].frameStartTimestamp > lastStamp) { lastStamp = ...; cpu = ...; gpu = ...; }
if (float.IsNaN(cpu) && !timingAvailable) cpu = Time.unscaledDeltaTime * 1000f;
samples.Add(new Sample { ... });   // 结构体，零分配
```

**为什么这样写**（每一行背后都有一个案例或原则）
| 写法 | 原因 |
| --- | --- |
| 关 VSync、不限帧率 | 测 GPU 能力，不是显示器刷新率 |
| 镜头按路径点平滑插值、按时间归一化 | 每次运行看到的画面一致，结果才可比 |
| 每个区域先在起点停几秒 | 让流式加载、着色器编译、粒子起转结束，测的是稳态 |
| 开头丢 `max(maxQueuedFrames,2)+4` 帧 | 启动帧的计时会在几帧后才到达（CASE-07） |
| `frameStartTimestamp` 去重 | 连续两次调用可能返回同一个已完成帧（CASE-07） |
| 拿不到新数据就留空 | 用 `unscaledDeltaTime` 补位会把同一帧算两次（CASE-07） |
| 每帧只写结构体，最后统一格式化 | 测量工具自己产生垃圾会触发 GC，干扰被测对象（CASE-08） |
| 预分配列表容量 | 列表扩容也是分配 |
| `gc` 列 | 诊断卡顿是否和 GC 同帧（CASE-08） |
| 文件头写 commit/API/设备/档位 | 让 `compare.py` 能自动判断两份数据是否可比 |

**换种写法会怎样**
- 用 `Time.deltaTime` 测帧时间：只有 CPU 视角，而且是上一帧的；在 GPU 瓶颈时测出来的是"CPU 等 GPU 的时间"，分不清瓶颈在哪。
- 实时写文件：每帧一次 I/O，扰动更大。

**可能踩的坑**
- `FrameTimingManager` 需要在 Player Settings 里打开 Frame Timing Stats，否则 `gpu_ms` 全空（`:16` 注释）。
- ProfilerRecorder 的 `LastValue` 第一次读取时是**从启动以来的累计值**（CASE-07 第 0 行 29124 个 Draw Call）——这也是丢弃启动帧的原因之一。

## 11. compare.py 怎么判定回退

`compare.py:29, 87-107, 170-226`；`thresholds.json`

**在干什么**
1. 读两份 CSV，解析 `#` 开头的文件头（用 `shlex` 处理带引号的设备名，`:41-48`）。
2. **可比性**：`MATCH_KEYS = ("api", "device", "tier")`（`:29`），任一不同 → 打印原因，退出码 2。
3. **阈值**：命令行 > `thresholds.json` 第一条匹配规则 > 默认 5%，并打印来源（`:205-209`）。
4. 每个区域算 GPU 平均、p95、CPU 平均、1% Low、Draw Call（`:96-107`）。
5. **判定**：`(新 GPU 平均 - 旧) / 旧 > 阈值` → 该区域标红，整体退出码 1（`:211-226`）。
6. 写 HTML 报告。

**为什么这样写**
- **拒绝比较不同条件的数据**：比较 D3D12 和 Vulkan 的数字然后报"回退"，是性能工具最常见的误报来源。
- **阈值按平台**：M5 Max 帧时间不到 3 ms，同一个包跑两次湖区就差了 4.9%（`docs/perf/README.md` 噪声实验）→ 5% 会误报，所以 Apple 用 8%。每条规则必须写 `why`。
- **退出码区分 0/1/2**：CI 脚本可以区分"通过""回退""输入有问题"，后者不应该被当成回退。
- **1% Low 的定义**（`:87-93`）：最慢的 1% 帧的平均帧率，用的是 `max(cpu, gpu)` 作为帧时间。
- 只用标准库：Windows 测试机上不用装 pip。

**换种写法会怎样（也是改进方向）**
- 只看平均值：一次 100 ms 的卡顿在 7000 帧的平均里几乎看不见 → 应该加 p95 / 1% Low 的阈值判定（目前只报告、不判定）。
- 单次比较：噪声大时容易误报 → README 里建议"连续两次超阈值才报警"，**但代码里还没实现**。
- 统计检验（比如 Mann-Whitney U）：比固定百分比更科学，但要求每边多次运行。

**可能踩的坑**：基线本身要可信——如果基线是在机器发热或后台有任务时跑的，后面所有比较都会偏。

## 12. screenshot_diff.py 与 PSO 预热

### 12a. screenshot_diff.py（`:107-121`）
```python
d = max(abs(pa[o]-pb[o]), abs(pa[o+1]-pb[o+1]), abs(pa[o+2]-pb[o+2]))   # 单像素：三通道最大差
if d > pix_thr: over += 1                                                # 超过 16/255 算"变了"
return total / (n*3), over / n, heatmap                                   # 平均差、变化比例、热力图
```
- **为什么两个阈值**：只看平均差，大面积轻微色偏和小范围严重错误可能得分相同；"超过 16 的像素比例 > 1%"抓的是**局部明显变化**，平均差抓的是**整体偏移**。
- **为什么要确定性截图**：粒子、火把闪烁、热浪都和时间有关，不冻结的话两次截图天然不同（`ScreenshotMode` 固定随机种子和模拟时间）。
- **局限**：逐像素比较对抗锯齿、半像素偏移很敏感；更"像人眼"的指标有 SSIM、FLIP（《荒原伙伴》的超分评测计划用这些）。
- 坑：两张图尺寸不同直接返回 `None`（`:109-110`），要在报告里显式标出，不能当作"没有差异"。

### 12b. PSO 预热（`ShaderWarmup.cs:27-61`）
```csharp
foreach (var path in Directory.GetFiles(dir, $"gsc_{SystemInfo.graphicsDeviceType}_*.graphicsstate")) {
    var gsc = new GraphicsStateCollection();
    if (!gsc.LoadFromFile(path)) continue;
    gsc.WarmUp().Complete();            // 同步等待：放在加载画面里
    states += gsc.totalGraphicsStateCount;
}
```
- **为什么按 API 分文件**：PSO 是图形 API 相关的，Metal 的状态对 D3D12 没用。
- **为什么每个档位一份**：不同档位的 URP Asset 打开了不同的 MSAA、深度纹理、不透明纹理 → 渲染目标格式和着色器变体不同 → PSO 不同（CASE-06 第 2 步）。
- **为什么同步 `Complete()`**：简单；代价是启动多约 0.9 秒。改进：异步预热 + 进度条，或者只同步预热第一个区域需要的、其余后台进行。
- **验收用数字，不用"没报错"**：日志打印状态数（`:41`、`:60`）——CASE-06 就是靠"0 个状态"这个数字发现的。
- 坑：着色器或材质改了以后，旧的录制文件会漏掉新状态 → 需要在 CI 里定期重录（**未实现**）。

# 第二部分：案例完整排查过程

> 面试讲案例的固定结构：**现象（一句话、带数字）→ 我的第一反应/假设 → 用什么工具检验 → 发现了什么 → 根因 → 怎么修 → 怎么证明修好了 → 沉淀了什么（工具/规则/文档）**。
> 以下 5 个都是真实记录在 `docs/cases/` 里的，**全部在 Apple M5 Max · Metal 上发现**。

## 案例 A · CASE-05：档位越高阴影越糊（档位设计问题）

| 步骤 | 内容 |
| --- | --- |
| 现象 | 跑完四档后检查 `Player.log`，四个档位都有 URP 警告："Reduced additional punctual light shadows resolution by 4 to make 48 shadow maps fit in the 2048x2048 shadow atlas"（High）。视觉上 High 的点光源阴影比 Medium 还糊 |
| 假设 | 档位参数之间互相冲突：投影灯数、单张分辨率、图集大小三者独立配置 |
| 检验 | 算账：点光源阴影 = 立方体 = 6 个面。High 是 8 盏 × 6 = 48 张，每张 1024² → 需要约 50 M 像素；图集 2048² 只有约 4.2 M |
| 根因 | 图集装不下时，URP **不报错**，而是把所有阴影统一降分辨率直到放得下。于是 High 的单张分辨率反而低于 Medium |
| 修复 | `ProjectSetup` 同时规定图集大小和单张分辨率，并加断言 `灯数 × 6 × 单张² ≤ 图集²`（`Assets/Editor/ProjectSetup.cs:91-95`）。新配置：Low 2 盏/256/1024，Medium 4/256/2048，High 8/512/4096，Ultra 16/512/8192 |
| 代价 | Ultra 的 8192² 图集约 128 MB 显存 → 显存 < 4 GB 的设备被硬件上限限制在 Medium |
| 验证 | 四档重跑，日志里这条警告出现 0 次（`run_mac_suite.sh` 会打印每档计数）。High 的 GPU 时间**上升** 11–16%（入口 1.80 → 2.06 ms）——因为现在真的在画 512² 的阴影 |
| 沉淀 | ① 档位表参数间的约束写成断言；② 引擎日志里的"降级"警告当作测试失败；③ "变慢"不一定是回退，要在回归记录里注明原因 |

**面试讲法要点**：这个案例最有价值的点是"修复让性能变差了，而这是对的"——说明你理解性能数字要和画质一起看。

## 案例 B · CASE-07：1 秒"卡顿"其实是启动帧（测量工具的 bug）

| 步骤 | 内容 |
| --- | --- |
| 现象 | 冷缓存 PSO 预热实验，入口"入区峰值"：有 GSC 1150 ms、无 GSC 1020 ms——**加了预热反而更糟**；1% Low 只有 31–33 fps |
| 第一反应 | 结论违反常识 → 先怀疑测量，不急着怀疑 GSC |
| 检验 | 不看汇总，逐帧看 CSV 前 12 行。发现：第 0 行 Draw Call 29124（一帧不可能画这么多）；第 0 行和第 3 行 CPU 时间几乎完全相同（1020.429 vs 1020.384 ms） |
| 根因 | ① ProfilerRecorder 第一次读是启动以来的累计值；② FrameTimingManager 的数据晚 2–3 帧到达，第 0 行拿不到新数据时代码用 `unscaledDeltaTime` 补位——那是上一帧（场景加载 + 预热）的时长；第 3 行 GPU 做完那帧后，FrameTimingManager 又正式交了一次 → **同一帧记了两次** |
| 修复 | `PerfRunner.cs:83-94, 114-127`：开头丢弃 `max(maxQueuedFrames,2)+4` 帧；按 `frameStartTimestamp` 去重；拿不到就留空，只有平台完全不支持时才退回 `unscaledDeltaTime` |
| 验证 | 同一实验各 3 次冷启动：启动帧不再出现；剩下的 >16.7 ms 帧只有真实的 PSO 编译——无 GSC 入口约 71 / 48 ms + 熔炉约 20 ms，有 GSC 时 0–1 个 |
| 沉淀 | 异步回读的计时数据（GPU 时间戳、FrameTimingManager、Profiler 计数器）都要考虑**延迟和去重**；"数字离谱先看原始逐帧数据" |

**面试讲法要点**：这是"排查性能问题第一步是确认数据可信"的最好例子。一个 1 秒的尖刺能把 1% Low 从约 400 fps 拉到 30 fps。

## 案例 C · CASE-06 + PSO 预热实验：Release 包"录制成功"却是空的（新 API 验收）

| 步骤 | 内容 |
| --- | --- |
| 背景 | 想用 Unity 6 的 GraphicsStateCollection 消除首次出现特效时的 PSO 编译卡顿 |
| 现象 | Release 包带 `-gsc-record` 跑，`BeginTrace()` 和 `SaveToFile()` 都返回 true，文件里 0 个状态，无任何警告 |
| 检验 | 换 Development 包，同场景同路线 → 33 个状态 / 33 个变体 |
| 根因 | PSO 追踪依赖 Development Player 的运行时钩子，Release 包里是空操作；API 不报告这一点 |
| 处理 | 形成工作流：Development 包 × 每档各录一份 → 拷进 `StreamingAssets/gsc_<API>_<tier>.graphicsstate` → Release 包启动时全部预热。D3D12 / Vulkan 要在 Windows 上各录一份 |
| 验证 | High 档，每次运行前清空 Metal 着色器缓存（避免驱动缓存掩盖结果），有/无 GSC 各 3 次：入口首段峰值 71.5 → 约 3.7 ms；>16.7 ms 的帧 3–4 个 → 0–1 个；入口 1% Low 约 235 → 372 fps（+60%）；代价是启动多 914–922 ms |
| 沉淀 | 新 API（尤其 Experimental 命名空间）"没报错"≠"生效了"，要用可观测的数字验收；性能实验要控制缓存状态 |

## 案例 D · CASE-08：地下湖偶发卡顿（排除法 + 观察者效应）

| 步骤 | 内容 |
| --- | --- |
| 现象 | 冷启动实验里，地下湖约一半的运行出现**一帧** 12–26 ms 卡顿，有没有 GSC 都会出现 |
| 复现 | `-perfrun -tier=high -perf-warmup 0 -perf-seconds 8`，约 5 次出现 2 次 |
| 排除 PSO | 有 GSC 预热时照样出现 → 排除 |
| 排除 GPU | 卡顿帧的 gpu_ms、Draw Call、SetPass 和前后帧一样 → 只在 CPU 侧 |
| 排除场景物体 | 卡顿出现在湖区路径的 51% / 65% / 10% 处，位置不固定 → 与位置无关 |
| 排除 GC | 给 CSV 加 `gc` 列：卡顿帧离最近的 GC 有 9 / 161 帧，GC 那一帧只有约 1 ms → 排除 |
| 未完成 | 操作系统调度 / 窗口服务器——需要 Development 包 + Profiler/Instruments 看主线程 → **待查** |
| 顺带发现 | 加了 `gc` 列后发现每约 600 帧一次 GC（24 秒 38 次）。来源：① PerfRunner 每帧格式化字符串；② 设置菜单的 `OnGUI` 即使直接 return 也会为 Layout 事件分配；③ `List.Sort(Comparison)` 每次包一个比较器 |
| 修复 | PerfRunner 改为写结构体、最后统一格式化；菜单关闭时 `useGUILayout = false`、HUD 每秒更新 4 次；排序用缓存的 `IComparer` |
| 验证 | 每次运行 GC 次数：38 → 27（只改 PerfRunner）→ 5（全部改完）。湖区卡顿修复后仍然出现（3 次中 2 次）→ 再次证明和 GC 无关 |
| 结论 | 约 0.4 次/运行、只影响 CPU 的单帧卡顿，对区域平均可忽略（约 7000 帧），影响 1% Low；先记录，换正式素材或上 Windows 复现后再决定是否深挖 |

**面试讲法要点**：① 每个假设都对应一个可以证伪的检验；② 主动说"这个问题我没有解决，原因是……，下一步是……"比编一个结论可信得多；③ 测量工具必须"安静"。

## 案例 E · CASE-04：湖面没有反射（工程配置静默关闭功能）

| 步骤 | 内容 |
| --- | --- |
| 现象 | 地下湖湖面始终纯黑，看不到火把倒影；`LakeReflection` 已调用 `RenderProbe()`，无报错 |
| 推理 | 湖面材质反照率接近黑、光滑度 0.96 → 看到的颜色几乎全部来自反射探针 → 问题在探针 |
