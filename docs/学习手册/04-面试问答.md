## B. 原生插件与能力探测（5–9）

### 5. 原生插件是怎么拿到 GPU 信息的？
- Unity 加载插件时调 `UnityPluginLoad`，插件拿 `IUnityGraphics` 并注册设备事件回调。
- 设备初始化事件里，按 `GetRenderer()` 判断 API，通过对应的 `IUnityGraphicsMetal / D3D12v7 / Vulkan` 接口拿到 Unity 已经创建好的原生设备，直接查询能力。
- 结果序列化成 JSON 缓存；C# 用 `[DllImport]` 调 `GpuCaps_GetReportJson` 拷走。
- 证据：`NativePlugins/GpuCaps/src/GpuCaps.cpp:41-112`；`Packages/com.zfw.gpucaps/Runtime/GpuCaps.cs:19-54`。

### 6. 为什么在设备事件里采集，而不是 C# 调用时现查？插件晚加载怎么办？
- 冷启动时插件可能早于设备创建，那时碰设备会崩。
- 插件如果是被第一次 `[DllImport]` 调用时才加载，设备早就建好了、事件不会再来 → `UnityPluginLoad` 里手动补调一次初始化。
- 有锁（`std::mutex`），因为事件可能来自渲染线程。
- 证据：`GpuCaps.cpp:1-10`、`:88-95`、`:37`、`:69`。

### 7. Metal 部分为什么要单独一个 .mm 文件？
- Unity 的 Metal 头文件里用了 `id<MTLDevice>`，只能在 Objective-C++ 里编译；`UnityMetalBridge.mm` 是唯一包含它的地方，把设备当 `void*` 交回 C++。
- 优先用带版本号的 `IUnityGraphicsMetalV2/V1`，旧接口已弃用。
- CMake 设符号默认隐藏，只导出 4 个函数。
- 证据：`src/UnityMetalBridge.mm:1-15`；`CMakeLists.txt:13-14`；提交 `3a89e24`。

### 8. 能力报告的结构是什么？为什么有两层？
- `schema` 版本号、`api`、`source`（native / systeminfo）、`gpu`（名称、vendorId、显存）、`driver`（可读版本 + 原始值）、`os`、`features`（bindless / raytracing / vrs / meshShader / shaderModel，每项 `value` + `raw`）、`unity`（SystemInfo）、`error`。
- 两层：原生层回答"硬件能不能"，unity 层回答"Unity 当前配置能不能用"（CASE-02）。
- `raw` 记原始枚举，便于排查判断依据。只加可选字段时 schema 不升。
- 证据：`src/CapsReport.h:13-79`；`Runtime/GpuCapsReport.cs:7-46`；`docs/cases/CASE-02-*.md`。

### 9. 各 API 的"显存""光追"是怎么判断的？有什么坑？
- Metal：显存用 `recommendedMaxWorkingSetSize`（统一内存没有"独显显存"）；光追 `supportsRaytracing` + Apple9 才算硬件，否则 emulated。
- D3D12：DXGI `DedicatedVideoMemory`；`D3D12_OPTIONS5.RaytracingTier`；Pascal 上 DXR 是驱动模拟 → emulated。
- Vulkan：DEVICE_LOCAL 堆之和（集显上是系统内存）；看有没有 `VK_KHR_ray_tracing_pipeline`。
- 坑：同一 GPU 不同 API 答案不同（CASE-01：M5 Max Metal 38 GB vs MoltenVK 48 GB，光追/VRS/Mesh 都不一样）→ **按"设备 × API"记录**。
- 证据：`src/CapsMetal.mm:37-63`；`src/CapsD3D12.cpp:52-91`；`src/CapsVulkan.cpp:68-98`；CASE-01。
- 注意：D3D12 / Vulkan 后端**写了但没编译、没在 Windows 跑过**。

## C. 画质分级与兼容（10–13）

### 10. 自动选档的逻辑？
- 硬件上限：非独显 → Low；显存 < 4 GB → Medium；否则 Ultra。（Apple 芯片按"类独显"处理。）
- 跑分：熔炉大厅（最重）High 档，预热 1 秒 + 采 5 秒 GPU 平均；≤ 11 ms Ultra、≤ 14 High、≤ 20 Medium、否则 Low；拿不到 GPU 时间用 CPU 时间，都没有给 Medium。
- 结果 = min(跑分, 上限)，再套兼容规则上限；决策和输入全部写日志。
- 存档：GPU 名或驱动版本变了就重新跑分；玩家手动选择优先。
- 证据：`TierSelector.cs:12-53`；`Assets/Scripts/Boot/TierBenchmark.cs:21-65`；`QualityTiers.cs:71-79`。

### 11. 兼容规则表怎么设计？现在有多少条规则？
- 规则字段：api、vendor、driverMin/Max（逐段数字比较）、disable（功能名列表）、maxTier、case（必填案例编号）。
- 启动时匹配当前设备，汇总要关闭的功能和最低的档位上限；设置界面显示应用了哪些案例。
- **现在 0 条**：`StreamingAssets/compat_overrides.json` 不存在。机制完整、有单元测试，但没有真实规则——因为所有案例都在一台 Mac 上发现，没有需要按设备回退的。
- 证据：`CompatOverrides.cs:11-66`；`QualityTiers.cs:114-137`。

### 12. 为什么档位里有"约束断言"？
- CASE-05：点光源阴影每盏 6 面，High 8 盏 × 6 × 1024² 远超 2048² 图集，URP 不报错而是统一降分辨率 → High 比 Medium 还糊。
- 修复：同时规定图集和单张分辨率，断言 `灯数 × 6 × 单张² ≤ 图集²`；把引擎的"降级"警告当测试失败。
- 证据：`Assets/Editor/ProjectSetup.cs:91-95`；`docs/cases/CASE-05-*.md`。

### 13. 为什么游戏专属字段要用 TierExtension？
- 包要通用：不能出现"热浪""湖面反射"。
- `[SerializeReference] List<TierExtension>`：多个模块可以各挂自己的子类；不用让游戏继承 TierSettings（那样已有资产要换脚本类型）。
- 证据：`TierSettings.cs:30-59`；`Assets/Scripts/Rendering/MineTierExtension.cs`；`~/dev/WildPartner/docs/DECISIONS.md` 阶段 0。

## D. 性能工具与排查（14–20）

### 14. PerfRunner 怎么采集？CSV 有哪些列？
- `-perfrun` 启动 → 找场景里的 PerfZone（按 order）→ 每区预热 3 秒 + 采 20 秒 → 相机沿区域曲线飞 → 写 CSV → 退出。
- 列：`frame,zone,cpu_ms,gpu_ms,draw_calls,setpass_calls,gfx_mem_mb,gc`；表头带 commit / api / device / tier / unity 版本 / 日期。
- 数据源：FrameTimingManager（CPU/GPU）、ProfilerRecorder（Draw Call、SetPass、显存）、`GC.CollectionCount(0)`。
- 证据：`Packages/com.zfw.perfrunner/Runtime/PerfRunner.cs:57-195`；`docs/perf/README.md` "CSV 格式"。

### 15. compare.py 怎么判断回退？阈值怎么定？
- 读两个 CSV；api / device / tier 有任何不同 → 拒绝比较，退出码 2。
- 逐区域比 GPU 平均 ms，增幅 > 阈值 → 回退，退出码 1；否则 0。同时输出 p95、CPU、1% Low 和曲线的 HTML 报告。
- 阈值：`thresholds.json` 按设备/API/档位匹配，每条规则写依据。实测同包两次 High 运行差 0.4% / 4.9% / 1.8% → Apple 8%，默认 5%。
- 退出码设计就是给 CI 用的（CI 本身没搭）。
- 证据：`Tools~/compare.py:29`、`:184-226`；`Tools~/thresholds.json`；`docs/perf/README.md` "噪声与回归阈值"。

### 16. screenshot_diff.py 做什么？发现过什么？
- 两个目录同名 PNG 逐张比较：平均绝对差（0–255）+ 超过像素阈值（默认 16）的像素比例，超过失败比例（默认 1%）判失败；输出热力图 HTML。只用 Python 标准库（自己解析 PNG）。
- 截图模式要"画面确定"：火光冻结、粒子固定种子、热浪固定时间，否则每次都不一样。
- 真实用途：CASE-04 湖面反射修复后用固定机位截图确认。
- 证据：`Tools~/screenshot_diff.py:4-7`、`:107`；`README.md` `-shots` 参数；CASE-04。

### 17. 🔥 PSO 预热实验：第一次结论是"预热反而更卡"，你怎么发现是测量错了？
- 现象：入口"入区峰值"有 GSC 1150 ms、无 GSC 1020 ms，1% Low 只有 31–33 fps。数字离谱。
- 动作：**不看汇总，看原始 CSV 前 12 行**。
- 线索 1：第 0 行 29124 个 Draw Call —— 不可能一帧画出来，ProfilerRecorder 第一次读是启动以来的累计值。
- 线索 2：第 0 行和第 3 行 CPU 时间几乎相同（1020.43 / 1020.38）→ 同一帧被记了两次：第 0 行拿不到新数据退回 `unscaledDeltaTime`（上一帧 = 加载那帧），第 3 行 FrameTiming 晚到又交了一次。
- 根因：FrameTimingManager 有 2–3 帧延迟，且可能重复返回同一帧。
- 修复：开始前丢弃 `max(maxQueuedFrames,2)+4` 帧；按 `frameStartTimestamp` 去重；没新数据就留空。
- 修复后真结论：无 GSC 入口 ~71 / ~48 ms 两帧卡顿 + 熔炉 ~20 ms；有 GSC 0–1 个；入口 1% Low +60%；代价启动 +0.9 s。
- 证据：`docs/cases/CASE-07-*.md`；`PerfRunner.cs:83-127`；`docs/perf/README.md` "PSO 预热实验"。

### 18. 🔥 地下湖偶发卡顿，你是怎么排查的？结论是什么？
- 现象：冷启动约一半运行出现一帧 12–26 ms，有无 GSC 都有。
- 排除法，每个假设一个可证伪的检验：
  - PSO？有 GSC 也出现 → 排除。
  - GPU？卡顿帧 gpu_ms、Draw Call、SetPass 和前后一样 → 只在 CPU。
  - 场景某物体？出现在路径 51% / 65% / 10%，位置不固定 → 排除。
  - GC？**加 `gc` 列**，卡顿帧离最近 GC 9 / 161 帧，GC 那帧才 ~1 ms → 排除。
  - 系统调度？需要 Development 包 + Instruments → 待查。
- 结论：约 0.4 次/运行、只影响 CPU 的一帧卡顿，对平均值无影响，影响 1% Low；先记录，换正式素材或上 Windows 后再决定。
- 顺带发现：**测量工具自己在制造垃圾**（每 ~600 帧一次 GC）→ 每帧零分配、菜单关闭时 `useGUILayout=false`、缓存比较器 → GC 38 → 5 次/运行。
- 证据：`docs/cases/CASE-08-*.md`；提交 `2eab251`。

### 19. 🔥 修了阴影图集之后 High 档变慢了 11–16%，这算回退吗？
- 不算，是"正确的代价"：原来 URP 偷偷降了阴影分辨率，修复后 High 真的在画 512² 的阴影。
- 关键是流程：**这种变化要在回归记录里写明原因**，而不是当成回退去"优化"回来。
- 引申：回退判断不能只看数字，要看画面是否等价（screenshot_diff）和是否有意为之。
- 证据：`docs/perf/README.md` "四档基线"读法；`docs/perf/mac/tiers_before_case05.md` vs `tiers_after_case05.md`。

### 20. 动态光源很多（91 盏），怎么控制开销？
- `TierLightManager`：每隔一段时间给所有火把打分 = 优先级 × (0.5 + 朝向) / (1 + 距离)，只让前 N 盏投影，N = 档位的 `maxShadowedPointLights`（Low 2 / Medium 4 / High 8 / Ultra 16）。
- 用缓存的 `IComparer` 排序，避免每次分配。
- Forward+ 负责"每块屏幕只算影响它的灯"，阴影预算负责最贵的部分。
- **没有**这项优化的前后对比数据（见简历核对）。
- 证据：`Assets/Scripts/Rendering/TierLightManager.cs:33-63`；CASE-05 档位表。
