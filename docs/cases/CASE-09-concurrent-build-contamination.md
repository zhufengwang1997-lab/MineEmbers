# CASE-09 同一台机器上另一个工程在构建，性能数据被“污染”

- 平台：Metal / Apple M5 Max / 四档 / 换上正式素材后的第一次采集
- 现象：素材版 Low 档的 1% Low 从白模的 581 / 754 / 771 fps 跌到 98 / 128 / 306 fps，但 **GPU 平均时间几乎不变**（0.68 → 0.74 ms）。
- 复现：同时在另一个窗口对另一个 Unity 工程执行 `BuildMac`（Unity 进程占 95% CPU），再跑 `tools/run_mac_suite.sh`。

## 定位

| 检查 | 看到的 | 说明 |
| --- | --- | --- |
| 慢帧在哪一侧 | 476 个 5–7 ms 的帧，`cpu_ms` 高、`gpu_ms` 正常 | 不是素材让 GPU 变重 |
| 慢帧的分布 | 均匀散落在整条路径，不集中在某个区域或某个机位 | 不像“某个物体”的问题 |
| 是否 GC | 慢帧所在帧的 `gc` 列全为 0 | 排除 GC（CASE-08 加的诊断列派上用场） |
| 机器上还有什么 | `pgrep -fl Unity` 看到另一个 `-batchmode -projectPath …/WildPartner` 进程 | 找到原因 |

根因：M5 Max 上一帧只有 1–2 ms，CPU 只要被别的进程抢走几毫秒，就会直接变成一个慢帧。平均值几乎不受影响，**1% Low 这种看尾部的指标会被放大好几倍**。

## 修复

`tools/run_mac_suite.sh` 增加 `quiet()`：每次运行前

1. 如果有其他 Unity 编辑器或命令行构建在跑，就一直等到它结束；
2. 把当时的系统负载（`vm.loadavg`）追加到 `out/suite/load.txt`，和结果放在一起。

这样数据旁边总能看到“测的时候机器是不是空闲的”，事后可以追查。

## 验证

另一个工程的构建结束后重跑：Low 档仅 CPU 侧的 >5 ms 帧从 **476 个降到 17 个**（6.7 万帧），1% Low 从 98–306 回到 226–236 fps。

但 High / Ultra 仍有约 450 个这样的帧：当时机器上还开着浏览器和其他客户端（WindowServer 占 46% CPU，负载 4.5–9.5）。`quiet()` 只能挡住 Unity 进程，挡不住一般的桌面程序。所以本轮素材版数据只用 GPU 平均值做结论，1% Low 留待在空闲机器上补测，见 [../perf/README.md](../perf/README.md) 的“换上正式素材后”一节。

## 教训

- 先看**平均值和尾部是否同向变化**：平均不变、尾部变差，多半是外部干扰，而不是被测对象变了。
- 测量结果要带上环境信息（负载、同时运行的进程），否则以后没法判断一份旧数据还能不能信。
- 在 CI 上就是“性能任务必须独占机器”：不能和编译任务共用一台 runner。
